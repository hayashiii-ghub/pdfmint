pdfmint, focused.

AIが作ったHTML / Markdownを、目的に合う日本語組版で提出用PDFへ仕上げるための最小ツールへ。

何を削り、何を強くしたか。

v0.xは便利な機能を少しずつ増やした結果、変換前に「どの仕組みを選ぶか」を考えるCLIになっていました。v1候補では、文書を仕上げることだけに戻します。

BEFORE / LEGACY 0.x

多機能だった。

変換に加え、運用や見た目の設定経路も抱えていました。

  • ×batch — 複数ファイルの一括処理
  • ×doctor — 環境診断コマンド
  • ×preset — memo / report / letter
  • ×brand profile — 自動探索と優先順位
  • ×Noto Sans / Serif の2書体
→

AFTER / V1 CANDIDATE

仕上げに集中する。

入口は1つ。選ぶのは原稿の目的に合う書体だけです。

$ pdfmint input.md output.pdf --font shippori --json入力、出力、必要なら書体。これで完結。

ローカル同梱する4書体

Zen Kaku Gothic New — 実務文書・表・仕様書（既定）

Shippori Mincho — 提案書・報告書・正式文書

Kiwi Maru — 案内・親しみのある資料

Klee One — 手紙・柔らかい一枚もの

開発・提出の流れは、4段だけ。

1.

原稿を用意する

AIが生成したHTMLまたはMarkdown。内容と構造は原稿側が持つ。

2.

書体を選ぶ

文書の目的から4つの書体を1つ選ぶ。選ばなければzen。

3.

必要なら確認を足す

PNGプレビュー、ページ数、用紙、余白だけを必要に応じて指定。

4.

PDFを受け取る

JSONからPDF・PNGの絶対パスとページ数を読み、提出物として扱う。

エージェントには、迷わないJSONを返す。

人間向けの対話フローではなく、成果物・書体・ページ数を機械的に判断できる出力です。成功だけで見た目が保証されるわけではないため、重要なレイアウトではPNGも生成して確認します。

  • ✓stdoutは最終結果JSONだけ
  • ✓Markdown時は実際に適用したfontを返す
  • ✓ページ数不一致は構造化エラー
  • ✓PNGは目視確認用の副成果物
{
  "success": true,
  "input": "/abs/report.md",
  "output": "/abs/report.pdf",
  "format": "A4",
  "font": "shippori",
  "page_count": 3,
  "png": {
    "output": "/abs/report.png"
  }
}

削っても、原稿を仕上げる力は残す。

HTML / Markdown原稿の形式はそのまま受け取る。
GFM拡張表・脚注・callout・コードハイライトを維持。
任意CSS案件固有の見た目は --css で上書き。
PDF + PNG提出用PDFと目視確認用PNGを同じ原稿から。
ページ数検証一枚ものの意図しない改ページを検出。
オフライン再現性Google Fontsへ接続せず、同梱フォントで描画。

操作は減らす。
日本語組版へのこだわりは、増やす。

4書体の実ウェイトをローカルに持つため、npm tarballは約33MBになります。この重さは汎用機能ではなく、環境に左右されない日本語PDFの品質に使っています。
