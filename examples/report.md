# 配信基盤リアーキテクチャ 技術選定レポート

現行の配信基盤は単一リージョン構成で、ピーク時のレイテンシ悪化と、障害時の影響範囲の広さが課題となっている。本レポートでは次期基盤の構成候補を比較し、採用方針を整理する。

> [!NOTE]
> 本レポートは社内検討用のドラフトです。数値は 2026 年 Q1 時点の実測値およびベンダー公称値に基づきます。

## 評価の観点

次の 4 点を重み付けして評価した。

1. **レイテンシ** — p95 応答時間
2. **可用性** — SLA と障害分離
3. **運用コスト** — 月額ランニング
4. **移行容易性** — 既存コードの改修量

## 構成候補の比較

| 構成 | p95 (ms) | 可用性 | 月額 (千円) | 移行 (人日) |
|---|---:|---:|---:|---:|
| 現行（単一リージョン） | 420 | 99.5% | 180 | — |
| マルチリージョン Active-Active | 180 | 99.99% | 540 | 45 |
| エッジキャッシュ + 単一オリジン | 150 | 99.9% | 320 | 20 |

エッジキャッシュ構成が、レイテンシと移行工数のバランスで最も優れる[^1]。

> [!WARNING]
> マルチリージョン Active-Active はデータ整合性の設計が複雑で、結果整合性を許容できない一部の機能とは相性が悪い。

## 移行イメージ

エッジ層のルーティングは、オリジンへのフォールバック付きキャッシュとして実装する。

```ts
// edge/router.ts
export async function handle(req: Request): Promise<Response> {
  const cached = await cache.match(req)
  if (cached) return cached

  const res = await fetch(originFor(req), { cf: { cacheTtl: 300 } })
  if (res.ok) await cache.put(req, res.clone())
  return res
}
```

> [!TIP]
> キャッシュ TTL は機能ごとに調整できる。更新頻度の低い静的メタデータは長め（1 時間）に設定すると、オリジン負荷をさらに下げられる。

## 推奨

- **短期**: エッジキャッシュ + 単一オリジンを採用し、p95 を 150ms 帯へ
- **中期**: トラフィック増を見て Active-Active を再評価する

移行は 2026 年 Q2 着手、Q3 完了を目標とする[^2]。

[^1]: 移行工数は既存ルーティング層の抽象度に依存する。本見積もりは現行コードの調査に基づく概算。
[^2]: 詳細スケジュールは別紙のロードマップを参照。
